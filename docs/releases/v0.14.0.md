## Аккаунты, эксплуатация и качество кода (v0.14)

Выпуск по итогам ревью: что происходит с учётными записями и установкой в неудачный день — утечка базы, отказ Valkey, несколько процессов сервера, бэкап в чужих руках. Плюс порядок в коде: большие файлы разбиты, помощники вынесены, импорты сортируются линтером.

**Учётные записи**

- Секреты двухфакторной аутентификации (TOTP) хранятся в базе зашифрованными ключом `SECRETS_KEY` из `.env` (AES-256-GCM): копия базы без ключа второго фактора не выдаёт. Секреты, записанные раньше, шифруются при первом успешном входе по коду.
- После ста неудачных попыток входа в учётную запись её владелец получает письмо со ссылкой на сброс пароля (не чаще раза за окно блокировки); сброс снимает блокировку. О попытках входа в несуществующие аккаунты никто не узнаёт.
- Ссылки из писем несут токен во фрагменте URL (`#token=`), а не в query-string: он не попадает в логи прокси и в `Referer`. Старые письма продолжают работать.
- Новая настройка инстанса «Требовать подтверждённый email»: пока адрес не подтверждён, нельзя создавать серверы, принимать приглашения, писать в ЛС и добавлять в друзья. Переключатель — в админке, значение по умолчанию задаёт `REQUIRE_VERIFIED_EMAIL` (в `docker-compose.yml` — `on`; без `SMTP_URL` выключите).

**Эксплуатация**

- Лимиты запросов при недоступном Valkey: вход, регистрация, сброс пароля и смена почты отвечают `503 RATE_LIMIT_UNAVAILABLE`, а не работают без лимита; остальные маршруты продолжают работать. Такие сбои считает метрика `chinchi_rate_limit_store_errors_total`; на дашборде — панель «Valkey в лимитах», в Prometheus — правила тревог (сервер не отдаёт метрики, ошибки Valkey, доля 5xx).
- Миграции базы идут под advisory-блокировкой Postgres: несколько процессов сервера можно запускать одновременно, миграции применит один.
- `backup.sh` шифрует архив, если задана `BACKUP_PASSPHRASE` (`openssl`, AES-256-CBC с PBKDF2), и предупреждает, если нет; `restore.sh` расшифровывает `.tar.enc`. В документации — расписание, ротация и копии вне машины.
- Политика CSP приложения больше не разрешает `'unsafe-inline'` для стилей. Smoke-тест CI проверяет заголовок, e2e проходят под той же политикой.
- Маршруты администратора проверяют права до валидации тела запроса: посторонний получает 401/403 без подробностей схемы.

**Код**

- Клиент SDK, сервисы сообщений, каналов и сборка зависимостей сервера разбиты по областям; общие `ok()` и `perUserRateLimit` в `http/`; порядок импортов проверяет eslint.
- Новые тесты: каждый маршрут `/admin/*` отвечает 403 не администратору и 401 анониму; property-тесты (`fast-check`) для парсера markdown и очистки метаданных картинок; e2e-проверки заголовков, флагов cookie, CSRF и 404 для чужих id.

## Обновление с 0.13.x

Нужен новый `docker-compose.yml` из релиза и две новые строки в `.env`:

```bash
./backup.sh
curl -fsSLO https://github.com/vogster/ChinchiChat/releases/download/v0.14.0/docker-compose.yml
# в .env:
#   SECRETS_KEY=$(openssl rand -hex 32)   — обязателен; храните вместе с S3_KMS_MASTER_KEY
#   REQUIRE_VERIFIED_EMAIL=on|off         — по умолчанию on; off, если SMTP_URL не задан
#   CHINCHI_VERSION=0.14.0
docker compose pull && docker compose up -d
```

Без `SECRETS_KEY` сервер не запустится (compose требует переменную). Если он потеряется позже, аккаунты с 2FA не смогут войти — делайте копию вместе с `.env`. Мониторинг: возьмите новый `docker-compose.monitoring.yml` и `chinchi-dashboard.json`, чтобы получить панель и тревоги.
