# Установка Chinchi на свой сервер

Chinchi разворачивается одним `docker compose` на одной машине: сервер API и realtime-шлюз, web-клиент, PostgreSQL, Valkey, S3-хранилище RustFS, LiveKit для голоса и видео и Caddy, который сам получает HTTPS-сертификаты. Образы готовые (GitHub Container Registry), на сервере нужны только два файла — `docker-compose.yml` и `.env`; клонировать репозиторий и что-то собирать не нужно.

## Что нужно

- Linux-сервер (x86-64) с Docker Engine 24+ и плагином Compose v2. Для небольшого сообщества хватит 2 vCPU и 4 ГБ памяти; голос и видео нагружают прежде всего сеть и процессор LiveKit.
- Одно DNS-имя, указывающее на сервер (запись A и/или AAAA), например `chat.example.com`. На нём всё: приложение и API, файлы (по пути `/chinchi/`) и сигнальный канал LiveKit (`/livekit/`), с одним HTTPS-сертификатом.
- По желанию — отдельные имена для файлов (`FILES_DOMAIN`, например `files.chat.example.com`) и голоса (`VOICE_DOMAIN`). Отдельный домен файлов полностью убирает загруженное пользователями с домена приложения; на основном домене файлы и так отдаются в «песочнице» (CSP `sandbox`, `nosniff`), где они не могут выполниться как приложение.
- Открытые порты: TCP 80 и 443 (Caddy), TCP 7881 и UDP 7882, 3478 (медиа LiveKit и встроенный TURN).
- Почтовый ящик с SMTP — для подтверждения email и сброса пароля (необязательно: без SMTP письма только пишутся в лог).

## Установка

```bash
mkdir chinchi && cd chinchi
curl -fsSLO https://github.com/vogster/ChinchiChat/releases/latest/download/docker-compose.yml
curl -fsSL -o .env https://github.com/vogster/ChinchiChat/releases/latest/download/env.example
```

Заполните `.env`: домен и секреты. Секреты удобно сгенерировать так:

```bash
openssl rand -base64 32
```

`LIVEKIT_API_SECRET` должен быть не короче 32 символов. `S3_KMS_MASTER_KEY` шифрует файлы на диске (см. «Шифрование данных»): сохраните его копию отдельно от бэкапов. Затем:

```bash
docker compose up -d
```

Миграции базы применяются при старте сервера, бакет хранилища и его CORS создаются автоматически. Когда все контейнеры здоровы (`docker compose ps`), откройте `https://chat.example.com` и зарегистрируйтесь. Администратором инстанса станет учётная запись с адресом из обязательной переменной `INITIAL_ADMIN_EMAIL` (с ним можно зарегистрироваться, даже если регистрация закрыта) — но только пока на инстансе нет ни одного администратора: позже этот адрес никаких прав не даёт. В разделе «Настройки → Администрирование» можно закрыть регистрацию или перевести её на приглашения (ссылки создаются там же), ограничить число серверов на человека, найти и заблокировать пользователя, удалить сервер. `REGISTRATION_MODE` задаёт только значение по умолчанию.

## Обновление

Версия Chinchi зафиксирована: скачанный `docker-compose.yml` запускает тот релиз, с которым он вышел, и сам по себе не обновится. Чтобы перейти на новый релиз, укажите его в `.env` и перезапустите:

```bash
# в .env: CHINCHI_VERSION=0.4.0
docker compose pull && docker compose up -d
```

Перед обновлением прочитайте заметки к релизу на GitHub — там будет сказано, если нужно взять и новый `docker-compose.yml`. Данные лежат в именованных томах Docker (`postgres-data`, `rustfs-data`, `valkey-data`, `caddy-data`) и при обновлении сохраняются.

## Сборка из исходников

Для разработчиков и тех, кто не хочет готовых образов:

```bash
git clone https://github.com/vogster/ChinchiChat.git && cd ChinchiChat
cp deploy/.env.example deploy/.env   # и заполнить
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.build.yml up -d --build
```

## Шифрование данных

- **Файлы** (вложения, аватары, эмодзи) хранилище шифрует само: у каждого объекта свой ключ, обёрнутый ключом KMS RustFS, а тот — мастер-ключом `S3_KMS_MASTER_KEY` из `.env`. Сервер при старте создаёт ключ KMS и включает шифрование бакета по умолчанию; браузеры загружают файлы как раньше. Копия тома `rustfs-data` без мастер-ключа бесполезна. Потеряете мастер-ключ — не прочитаете и файлы, поэтому храните его копию отдельно от бэкапов данных (менеджер паролей, сейф). Включается шифрование только для новых файлов: загруженные раньше остаются как были.
- **База и диск.** Шифровать отдельные поля в Postgres бессмысленно: ключ лежал бы на том же сервере. Шифруйте диск целиком: LUKS на Linux (`cryptsetup luksFormat` для раздела с `/var/lib/docker`), BitLocker на Windows Server, шифрование томов у облачного провайдера (у большинства включено по умолчанию — проверьте). Это защищает от кражи диска или снятого образа, но не от доступа к работающему серверу.
- **Переписка** в зашифрованных беседах шифруется на устройствах участников: сервер хранит только шифротекст ([как это устроено](encryption.md)).

## Резервные копии

Копировать нужно базу и хранилище файлов; Valkey хранит только временное состояние (онлайн-статусы, голос, лимиты). Для этого рядом с `docker-compose.yml` лежат два скрипта — `backup.sh` и `restore.sh` (файлы релиза начиная с v0.11; для более ранних версий возьмите их из `deploy/` в репозитории):

```bash
curl -fsSLO https://github.com/vogster/ChinchiChat/releases/latest/download/backup.sh
curl -fsSLO https://github.com/vogster/ChinchiChat/releases/latest/download/restore.sh
chmod +x backup.sh restore.sh
```

**Бэкап:**

```bash
./backup.sh            # архив в ./backups/chinchi-backup-<дата>.tar
./backup.sh /mnt/backup
```

Скрипт на время копирования останавливает сервер (обычно на секунды), чтобы база и файлы совпадали, и складывает в один архив дамп базы, файлы хранилища и версию Chinchi. Удобно запускать по расписанию, например из cron: `0 4 * * * cd /opt/chinchi && ./backup.sh`.

**Восстановление** — на этой же или на чистой машине с тем же `docker-compose.yml` и **тем же `.env`** (главное — тот же `S3_KMS_MASTER_KEY`):

```bash
docker compose up -d   # на чистой машине: сначала обычная установка
./restore.sh backups/chinchi-backup-2026-10-16-120000.tar
```

Скрипт спросит подтверждение (или `--yes`), заменит базу и файлы содержимым архива и запустит Chinchi. Версия установки должна быть не старше версии бэкапа — иначе скрипт откажется и подскажет, какую указать в `CHINCHI_VERSION`. Если установка новее, миграции применятся при старте.

Файлы в архиве зашифрованы ключом хранилища, а `.env` в архив не входит: храните `.env` (и особенно `S3_KMS_MASTER_KEY`) отдельно от бэкапов. Без мастер-ключа файлы из архива не прочитать. Зашифрованные беседы пользователей из бэкапа не расшифровать никому: ключи от них — на устройствах пользователей.

Цикл «бэкап → чистая установка → восстановление» проверен: учётные записи, сообщения и файлы возвращаются полностью.

## Голос и видео

- Браузеры подключаются к LiveKit по `wss://CHINCHI_DOMAIN/livekit` (или `wss://VOICE_DOMAIN`, если он задан), а медиа идёт напрямую по UDP 7882. Если UDP закрыт, LiveKit переходит на TCP 7881 или встроенный TURN (UDP 3478).
- LiveKit определяет публичный адрес сервера через STUN (`use_external_ip` в `LIVEKIT_CONFIG` внутри `docker-compose.yml`). Если у сервера несколько адресов или он за NAT провайдера, задайте адрес явно параметром `rtc.node_ip` там же.
- TURN поверх TLS (для очень строгих корпоративных сетей) по умолчанию не настроен: он требует отдельного домена с сертификатом, см. документацию LiveKit.

## Мониторинг

Сервер отдаёт метрики Prometheus на отдельном порту `9464` (`/metrics`): время ответа API по маршрутам, открытые соединения шлюза, отправленные и опубликованные события, фоновые задачи, а также стандартные метрики Node.js (память, CPU, задержка цикла событий). Порт открыт только внутри сети Docker и наружу не публикуется — добавьте свой Prometheus в ту же сеть и укажите цель `server:9464`. Вне Docker метрики включаются переменной `METRICS_PORT` и по умолчанию слушают только `127.0.0.1` (`METRICS_HOST`).

## Если что-то не работает

- `docker compose logs server` — сервер пишет в лог неверные переменные окружения (имя переменной, без значения).
- Сертификаты не выдаются — проверьте, что все три имени указывают на сервер и порт 80 доступен снаружи.
- Нет звука, хотя голосовой канал подключается — почти всегда это закрытые UDP-порты 7882 и 3478.
- Загрузки файлов падают — если задан `FILES_DOMAIN`, он должен открываться снаружи и указывать на этот же сервер.
