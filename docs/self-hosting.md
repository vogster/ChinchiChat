# Установка Chinchi на свой сервер

Chinchi разворачивается одним `docker compose` на одной машине: сервер API и realtime-шлюз, web-клиент, PostgreSQL, Valkey, S3-хранилище RustFS, LiveKit для голоса и видео и Caddy, который сам получает HTTPS-сертификаты. Образы готовые (GitHub Container Registry), на сервере нужны только два файла — `docker-compose.yml` и `.env`; клонировать репозиторий и что-то собирать не нужно.

## Что нужно

- Linux-сервер (x86-64 или ARM64 — например, Raspberry Pi 4/5, Ampere, Graviton) с Docker Engine 24+ и плагином Compose v2. Для небольшого сообщества хватит 2 vCPU и 4 ГБ памяти; голос и видео нагружают прежде всего сеть и процессор LiveKit.
- Одно DNS-имя, указывающее на сервер (запись A и/или AAAA), например `chat.example.com`. На нём всё: приложение и API, файлы (по пути `/chinchi/`) и сигнальный канал LiveKit (`/livekit/`), с одним HTTPS-сертификатом.
- Рекомендуется второе имя для файлов пользователей (`FILES_DOMAIN`, например `files.chat.example.com`), указывающее на тот же сервер: тогда загруженное пользователями живёт на отдельном origin и не соседствует с приложением. Без него файлы отдаются с основного домена в «песочнице» (CSP `sandbox`, `nosniff`), где они не могут выполниться как приложение, но отдельный домен — более надёжное решение по умолчанию. По желанию — своё имя и для голоса (`VOICE_DOMAIN`).
- Открытые порты: TCP 80 и 443 (Caddy), TCP 7881 и UDP 7882, 3478 (медиа LiveKit и встроенный TURN).
- Почтовый ящик с SMTP — для подтверждения email, сброса пароля и писем о блокировке входа. Без него письма не уходят, а значит никто не подтвердит адрес: тогда выключите `REQUIRE_VERIFIED_EMAIL` (по умолчанию `on`), иначе новые пользователи не смогут создавать серверы и писать в ЛС. Исключение — ссылка подтверждения для `INITIAL_ADMIN_EMAIL`: без SMTP она пишется в лог сервера (см. «Первый администратор» ниже).

## Установка

```bash
mkdir chinchi && cd chinchi
curl -fsSLO https://github.com/vogster/ChinchiChat/releases/latest/download/docker-compose.yml
curl -fsSL -o .env https://github.com/vogster/ChinchiChat/releases/latest/download/env.example
```

Заполните `.env` — обязательны домен `CHINCHI_DOMAIN`, пять секретов (`POSTGRES_PASSWORD`, `S3_SECRET_KEY`, `LIVEKIT_API_SECRET`, `S3_KMS_MASTER_KEY`, `SECRETS_KEY`) и ваш адрес в `INITIAL_ADMIN_EMAIL`; остальное (`FILES_DOMAIN`, почта, режим регистрации) — по желанию, полный список в разделе «Переменные `.env`» ниже. Секреты удобно сгенерировать так:

```bash
openssl rand -hex 32
```

Именно `-hex`: base64 содержит `/` и `+`, а из `POSTGRES_PASSWORD` собирается строка подключения к базе, и с такими символами она не разбирается — сервер не стартует и пишет об этом в лог. Если пароль уже задан, символы `/ @ # ?` в нём нужно закодировать как в URL (`%2F`, `%40`, `%23`, `%3F`) либо заменить пароль. `LIVEKIT_API_SECRET` должен быть не короче 32 символов. `SECRETS_KEY` (64 hex-символа) шифрует секреты двухфакторной аутентификации в базе: храните его копию вместе с `S3_KMS_MASTER_KEY` — без него пользователи с 2FA не смогут войти. `S3_KMS_MASTER_KEY` шифрует файлы на диске (см. «Шифрование данных»): сохраните его копию отдельно от бэкапов. Затем:

```bash
docker compose up -d
```

Образы собирает GitHub Actions и подписывает аттестацией сборки; при желании проверьте, что скачанное собрано из этого репозитория: `gh attestation verify oci://ghcr.io/vogster/chinchi-server:0.14.0 --owner vogster` (и так же `chinchi-web`). Перед публикацией образы проходят сканирование Trivy: релиз с незакрытой уязвимостью уровня HIGH/CRITICAL не выходит.

Миграции базы применяются при старте сервера, бакет хранилища и его CORS создаются автоматически. Когда все контейнеры здоровы (`docker compose ps`), откройте `https://chat.example.com` и зарегистрируйтесь с адресом из обязательной переменной `INITIAL_ADMIN_EMAIL` (с ним можно зарегистрироваться, даже если регистрация закрыта), затем подтвердите этот адрес по ссылке из письма — администратором учётная запись становится только после подтверждения, так что зарегистрироваться первым с вашим адресом и забрать инстанс нельзя. Это работает, пока на инстансе нет ни одного администратора: позже этот адрес никаких прав не даёт.

### Первый администратор без SMTP

Если `SMTP_URL` не задан, письмо не уходит, а ссылка подтверждения для `INITIAL_ADMIN_EMAIL` пишется в лог сервера отдельной строкой с меткой `FIRST ADMIN LINK` (только для этого адреса и только пока администратора нет — остальные одноразовые ссылки в лог не попадают). Найти её — в папке с `docker-compose.yml` после регистрации:

```bash
docker compose logs server | grep "FIRST ADMIN LINK"
```

В выводе — строка вида `… "msg":"FIRST ADMIN LINK: open it to confirm admin@example.com and become the instance admin (SMTP_URL is not set, so it was not emailed): https://chat.example.com/verify-email#token=…"`. Скопируйте адрес от `https://` до конца строки (без закрывающей кавычки) и откройте в браузере — входить для этого не нужно. Ссылка действует 24 часа; если опоздали, войдите и нажмите «Отправить ещё раз» на плашке о подтверждении email — новая ссылка снова появится в логе. Логи пишет контейнер `server`; `docker compose logs -f server` показывает их в реальном времени, `--since 10m` — только за последние 10 минут. В разделе «Настройки → Администрирование» можно закрыть регистрацию или перевести её на приглашения (ссылки создаются там же), ограничить число серверов на человека, найти и заблокировать пользователя, удалить сервер. Там же — переключатель «Требовать подтверждённый email»: пока адрес не подтверждён, нельзя создавать серверы, принимать приглашения, писать в ЛС и добавлять в друзья (читать и настраивать свой аккаунт можно). `REGISTRATION_MODE` и `REQUIRE_VERIFIED_EMAIL` (по умолчанию `on`) задают только значения по умолчанию. Без `SMTP_URL` письма никуда не уходят — тогда требование подтверждения стоит выключить.

## Обновление

Версия Chinchi зафиксирована: скачанный `docker-compose.yml` запускает тот релиз, с которым он вышел, и сам по себе не обновится. Чтобы перейти на новый релиз, сделайте бэкап, укажите версию в `.env` и перезапустите:

```bash
./backup.sh
# в .env: CHINCHI_VERSION=0.14.0
docker compose pull && docker compose up -d
```

Перед обновлением прочитайте [заметки к релизу](https://github.com/vogster/ChinchiChat/releases): в них сказано, нужно ли взять новый `docker-compose.yml` и добавить ли переменные в `.env` (так, v0.14 ввёл обязательный `SECRETS_KEY` и `REQUIRE_VERIFIED_EMAIL`). Миграции базы применяются при старте и только вперёд, поэтому откат на старую версию — это восстановление из бэкапа. Данные лежат в именованных томах Docker (`postgres-data`, `rustfs-data`, `valkey-data`, `caddy-data`) и при обновлении сохраняются.

## Шифрование данных

- **Файлы** (вложения, аватары, эмодзи) хранилище шифрует само: у каждого объекта свой ключ, обёрнутый ключом KMS RustFS, а тот — мастер-ключом `S3_KMS_MASTER_KEY` из `.env`. Сервер при старте создаёт ключ KMS и включает шифрование бакета по умолчанию; браузеры загружают файлы как раньше. Копия тома `rustfs-data` без мастер-ключа бесполезна. Потеряете мастер-ключ — не прочитаете и файлы, поэтому храните его копию отдельно от бэкапов данных (менеджер паролей, сейф). Включается шифрование только для новых файлов: загруженные раньше остаются как были.
- **Секреты 2FA** в базе зашифрованы ключом `SECRETS_KEY` из `.env` (AES-256-GCM); остальные секреты (пароли, сессии, коды восстановления) хранятся хэшами.
- **База и диск.** Шифровать остальные поля в Postgres бессмысленно: ключ лежал бы на том же сервере. Шифруйте диск целиком: LUKS на Linux (`cryptsetup luksFormat` для раздела с `/var/lib/docker`), BitLocker на Windows Server, шифрование томов у облачного провайдера (у большинства включено по умолчанию — проверьте). Это защищает от кражи диска или снятого образа, но не от доступа к работающему серверу.
- **Переписка** в зашифрованных беседах шифруется на устройствах участников: сервер хранит только шифротекст ([как это устроено](encryption.md)).

## Резервные копии

Копировать нужно базу и хранилище файлов; Valkey хранит только временное состояние (онлайн-статусы, голос, лимиты). Для этого рядом с `docker-compose.yml` лежат два скрипта — `backup.sh` и `restore.sh` (файлы релиза начиная с v0.11; для более ранних версий возьмите их из `deploy/` в репозитории):

```bash
curl -fsSLO https://github.com/vogster/ChinchiChat/releases/latest/download/backup.sh
curl -fsSLO https://github.com/vogster/ChinchiChat/releases/latest/download/restore.sh
chmod +x backup.sh restore.sh
```

**Бэкап:**

```bash
./backup.sh            # архив в ./backups/chinchi-backup-<дата>.tar
./backup.sh /mnt/backup
```

Скрипт на время копирования останавливает сервер (обычно на секунды), чтобы база и файлы совпадали, и складывает в один архив дамп базы, файлы хранилища и версию Chinchi.

**Шифрование архива.** Дамп базы в архиве — открытый текст: имена, адреса почты, хеши паролей, переписка незашифрованных каналов. Задайте `BACKUP_PASSPHRASE`, и скрипт зашифрует архив (`openssl`, AES-256-CBC с PBKDF2, расширение `.tar.enc`); без переменной он предупредит, что архив не зашифрован. Парольную фразу храните там же, где `.env`, — без неё архив не открыть.

**Расписание и ротация.** Удобно запускать из cron раз в сутки, удаляя копии старше месяца, и держать хотя бы одну копию вне этой машины (другой сервер, объектное хранилище через `rclone`): бэкап на том же диске не спасёт при его потере.

```bash
# /etc/cron.d/chinchi-backup
0 4 * * * root cd /opt/chinchi && BACKUP_PASSPHRASE="$(cat /root/.chinchi-backup-passphrase)" ./backup.sh /mnt/backup >>/var/log/chinchi-backup.log 2>&1 && find /mnt/backup -name 'chinchi-backup-*' -mtime +30 -delete
```

Раз в несколько месяцев проверяйте, что архив восстанавливается (ниже) — бэкап, который никто не пробовал развернуть, не бэкап.

**Восстановление** — на этой же или на чистой машине с тем же `docker-compose.yml` и **тем же `.env`** (главное — тот же `S3_KMS_MASTER_KEY`):

```bash
docker compose up -d   # на чистой машине: сначала обычная установка
./restore.sh backups/chinchi-backup-2026-10-16-120000.tar
```

Скрипт спросит подтверждение (или `--yes`), заменит базу и файлы содержимым архива и запустит Chinchi. Зашифрованному архиву (`.tar.enc`) нужна та же `BACKUP_PASSPHRASE`. Версия установки должна быть не старше версии бэкапа — иначе скрипт откажется и подскажет, какую указать в `CHINCHI_VERSION`. Если установка новее, миграции применятся при старте. Несколько процессов сервера (масштабирование, перезапуск без простоя) можно запускать одновременно: миграции применяет один, остальные ждут его под advisory-блокировкой Postgres.

Файлы в архиве зашифрованы ключом хранилища, а `.env` в архив не входит: храните `.env` (и особенно `S3_KMS_MASTER_KEY`) отдельно от бэкапов. Без мастер-ключа файлы из архива не прочитать. Зашифрованные беседы пользователей из бэкапа не расшифровать никому: ключи от них — на устройствах пользователей.

Цикл «бэкап → чистая установка → восстановление» проверен: учётные записи, сообщения и файлы возвращаются полностью.

## Голос и видео

- Браузеры подключаются к LiveKit по `wss://CHINCHI_DOMAIN/livekit` (или `wss://VOICE_DOMAIN`, если он задан), а медиа идёт напрямую по UDP 7882. Если UDP закрыт, LiveKit переходит на TCP 7881 или встроенный TURN (UDP 3478).
- LiveKit определяет публичный адрес сервера через STUN (`use_external_ip` в `LIVEKIT_CONFIG` внутри `docker-compose.yml`). Если у сервера несколько адресов или он за NAT провайдера, задайте адрес явно параметром `rtc.node_ip` там же.
- TURN поверх TLS (для очень строгих корпоративных сетей) по умолчанию не настроен: он требует отдельного домена с сертификатом, см. документацию LiveKit.

## Мониторинг

Сервер отдаёт метрики Prometheus на отдельном порту `9464` (`/metrics`): время ответа API по маршрутам, открытые соединения шлюза, время входа (READY), отправленные и опубликованные события, фоновые задачи, а также стандартные метрики Node.js (память, CPU, задержка цикла событий). Порт открыт только внутри сети Docker и наружу не публикуется.

Лимиты запросов хранятся в Valkey. Если он не отвечает, обычные маршруты продолжают работать без лимитов (метрика `chinchi_rate_limit_store_errors_total` считает такие проверки, панель «Valkey в лимитах» на дашборде краснеет), а вход, регистрация, сброс пароля и смена почты отвечают `503 RATE_LIMIT_UNAVAILABLE`, пока Valkey не вернётся: без лимита они стали бы мишенью для перебора.

**Готовый дашборд.** Нужен Docker Compose 2.23.1 или новее (файл задаёт конфиги Prometheus и Grafana прямо в compose). Рядом с установкой положите два файла из релиза и задайте пароль Grafana:

```bash
curl -fsSLO https://github.com/vogster/ChinchiChat/releases/latest/download/docker-compose.monitoring.yml
curl -fsSLO https://github.com/vogster/ChinchiChat/releases/latest/download/chinchi-dashboard.json
echo "GRAFANA_ADMIN_PASSWORD=$(openssl rand -hex 18)" >> .env
docker compose -f docker-compose.yml -f docker-compose.monitoring.yml up -d
```

Поднимутся Prometheus (хранит 30 дней, `PROMETHEUS_RETENTION`) и Grafana с дашбордом Chinchi на главной. В Prometheus заданы три правила тревог (`/alerts` в его интерфейсе): сервер не отдаёт метрики, Valkey не отвечает на проверки лимитов, больше 5% ответов API — 5xx; чтобы получать их почтой или в мессенджер, подключите Alertmanager. Grafana слушает только `127.0.0.1:3001` сервера — откройте её через SSH-туннель: `ssh -L 3001:localhost:3001 you@your-server`, затем `http://localhost:3001` (пользователь `admin`). Свой Prometheus можно подключить к сети Docker с целью `server:9464`, а дашборд импортировать из `chinchi-dashboard.json`. Вне Docker метрики включаются переменной `METRICS_PORT` и по умолчанию слушают только `127.0.0.1` (`METRICS_HOST`).

## Другой прокси перед Caddy

По умолчанию клиенты приходят прямо в Caddy, и всё работает без настройки: Caddy не верит заголовку `X-Forwarded-For` от клиентов и сам ставит в него реальный адрес, а сервер доверяет ровно одному хопу (`TRUST_PROXY=1` в `docker-compose.yml`). На этот адрес завязаны лимиты запросов, защита от перебора пароля и список сеансов в настройках.

Если перед Caddy стоит ещё один прокси — CDN, балансировщик облака, nginx или Traefik на этом же хосте (тогда обычно меняют `HTTP_PORT`/`HTTPS_PORT`), — Caddy видит адрес этого прокси, а не клиента. Без настройки все пользователи окажутся «с одного IP»: общие лимиты, и один неудачный пароль заблокирует вход всем. Укажите адреса прокси в `.env`:

```bash
# CIDR-диапазоны прокси через пробел
TRUSTED_PROXIES=10.0.0.0/8 2001:db8::/32
```

Caddy начнёт брать адрес клиента из `X-Forwarded-For`, но только в запросах от этих адресов и читая заголовок справа налево (`trusted_proxies_strict`), чтобы клиент не мог подставить чужой адрес слева. `TRUST_PROXY` у сервера менять не нужно: он по-прежнему видит перед собой только Caddy. Никогда не ставьте `TRUST_PROXY=true` — так сервер поверит любому значению заголовка, которое пришлёт клиент.

## Если что-то не работает

- `docker compose logs server` — сервер пишет в лог неверные переменные окружения (имя переменной, без значения). `DATABASE_URL: not a valid URL` почти всегда означает `/`, `+` или `@` в `POSTGRES_PASSWORD`: сгенерируйте его заново командой `openssl rand -hex 32`.
- Сертификаты не выдаются — проверьте, что все три имени указывают на сервер и порт 80 доступен снаружи.
- Нет звука, хотя голосовой канал подключается — почти всегда это закрытые UDP-порты 7882 и 3478.
- Загрузки файлов падают — если задан `FILES_DOMAIN`, он должен открываться снаружи и указывать на этот же сервер.
- `docker compose up` останавливается с `set SECRETS_KEY in .env` (или другой переменной) — после обновления с версии до 0.14 в `.env` не хватает новых обязательных строк; возьмите их из `env.example` релиза.
- Пользователи с 2FA не могут войти после переезда или восстановления — в `.env` другой `SECRETS_KEY`, чем тот, которым секреты были зашифрованы. Верните прежний ключ; если он потерян, пользователь входит по коду восстановления (они хранятся хэшами и от ключа не зависят), отключает 2FA в настройках и настраивает её заново.
- Вы зарегистрировались с `INITIAL_ADMIN_EMAIL`, но администратором не стали — адрес ещё не подтверждён. С SMTP — откройте ссылку из письма; без SMTP — возьмите её из лога: `docker compose logs server | grep "FIRST ADMIN LINK"` (подробнее — «Первый администратор без SMTP»).
- Новые пользователи жалуются, что не могут создать сервер или написать в ЛС (`EMAIL_NOT_VERIFIED`) — у них не подтверждён email. Проверьте, что `SMTP_URL` задан и письма доходят (`docker compose logs server | grep -i mail`), либо выключите «Требовать подтверждённый email» в админке.
- Вход и регистрация отвечают `503 RATE_LIMIT_UNAVAILABLE` — не отвечает Valkey: `docker compose ps valkey`, `docker compose logs valkey`. Остальное приложение в это время работает, но без лимитов запросов.
