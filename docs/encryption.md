# Шифрование в Chinchi: модель угроз и дизайн

Документ фазы 15. Сначала — от чего мы защищаемся и чего не обещаем, потом — как это устроено. Открытые вопросы решены: отдельный тип «Зашифрованная беседа» и второй этап до v1.0.

## 1. Что есть сейчас

- **В пути** всё идёт по TLS: браузер ↔ Caddy ↔ сервер, файлы — по HTTPS с домена хранилища, голос и видео — DTLS-SRTP до LiveKit.
- **На сервере** сообщения, файлы и метаданные лежат открыто: в Postgres, в S3 (RustFS), в бэкапах. Их видит любой, у кого есть доступ к машине, базе или бэкапу, и сам LiveKit (он расшифровывает медиа, чтобы раздать его участникам).
- Пароли — argon2id, сессии и резервные коды 2FA — хэши. **Секрет TOTP хранится открыто** (его нельзя хэшировать: сервер вычисляет по нему коды); его, как и всё остальное, защищает только шифрование диска. Шифровать его ключом с того же сервера смысла мало — ключ утёк бы вместе с базой; вынести ключ в KMS можно вместе с SSE (п. 6).

## 2. От кого защищаемся

| Кто                                                                                  | Что может сейчас            | После фазы 15                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------ | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Перехват в сети** (провайдер, публичный Wi-Fi)                                     | ничего (TLS)                | ничего                                                                                                                                                                                                 |
| **Утечка диска, бэкапа или бакета** (украли сервер, выложили бэкап)                  | читать всё                  | файлы в S3 зашифрованы ключом KMS; диск и бэкапы — по инструкции; содержимое зашифрованных ЛС бесполезно без ключей устройств                                                                          |
| **Любопытный или взломанный администратор инстанса** (доступ к базе, логам, LiveKit) | читать всё, слушать звонки  | не может читать зашифрованные ЛС и группы и слушать звонки в них; видит метаданные (см. ниже)                                                                                                          |
| **Злонамеренный администратор, который меняет код сервера или веб-клиента**          | всё                         | **не защищаемся полностью**: веб-клиент отдаёт тот же сервер. Защита — проверка собеседника (коды безопасности) и, позже, нативные клиенты (Desktop/Mobile), которые не обновляются с сервера инстанса |
| **Участник беседы**                                                                  | читать то, что ему прислали | то же: шифрование не защищает от собеседника                                                                                                                                                           |

**Что сервер видит всегда, даже в зашифрованных беседах:** кто с кем в беседе, когда и сколько сообщений и какого они размера, IP-адреса, кто в звонке и сколько он длится, список устройств пользователя. Это метаданные, без них сервер не может доставлять сообщения.

## 3. Где шифруем сквозным образом, а где нет

- **ЛС и группы ЛС — да.** Небольшие закрытые беседы, где важна приватность.
- **Звонки в ЛС и группах — да**, ключ звонка выводится из той же группы.
- **Текстовые каналы серверов — нет.** Там нужны поиск, модерация (удаление чужих сообщений, автомодерация, жалобы с текстом), боты и слэш-команды, вебхуки, история для новых участников. Так же устроены Discord и большие комнаты Matrix. Каналы серверов защищены шифрованием хранения.
- **Голосовые каналы серверов — пока нет.** Можно позже по образцу Discord DAVE (отдельная MLS-группа на голосовой канал); в фазу 15 не входит.

**Решено:** на первом этапе — отдельный тип «Зашифрованная беседа» (как секретные чаты Telegram): у старых ЛС ничего не ломается, а пользователь явно соглашается на ограничения (ниже). С одним человеком — одна зашифрованная беседа (рядом с обычной ЛС): кнопка в профиле открывает уже начатую. Когда появятся резервная копия ключей и нативные клиенты — сделать шифрование вариантом по умолчанию.

**Что теряется в зашифрованной беседе:**

- поиск на сервере (возможен только локальный поиск по уже расшифрованному на устройстве);
- превью ссылок (сервер не видит ссылок; делать превью на клиенте значит раскрыть IP сайту — выключено);
- боты, вебхуки, слэш-команды;
- история до момента, когда устройство вошло в беседу (без резервной копии, см. п. 6);
- текст в системных уведомлениях с сервера (push в будущих мобильных клиентах — «Новое сообщение»).

## 4. Протокол: MLS (RFC 9420)

MLS — стандарт IETF для групповых чатов со сквозным шифрованием: forward secrecy и post-compromise security, группы до тысяч устройств, удаление участника меняет ключи для всех. Его используют Webex, Discord (DAVE), Wire, RCS.

**Библиотека — [ts-mls](https://github.com/LukaJCB/ts-mls) 1.6.4** (MIT, TypeScript, без нативного кода).

- Работает в браузере (WebCrypto через `@hpke/core`) и на чистом JS (`nobleCryptoProvider` — для React Native).
- Набор шифров — `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`, обязательный по RFC 9420.
- **Риск: библиотека не проходила независимого аудита.** Меры: точная версия; вся работа с MLS — за своим интерфейсом в отдельном пакете (`packages/e2ee`), чтобы при необходимости заменить реализацию (запасной вариант — OpenMLS через WASM); тесты на векторах RFC; шифрование помечается «бета» до внешней проверки, перед v1.0.

**Проба (spike), результаты:**

- 4 устройства (у Алисы телефон и ноутбук, одно устройство — на чистом JS) создают группу одним коммитом, все читают сообщения друг друга.
- Сохранение состояния группы (`encodeGroupState`, ~1,9 КБ на 4 участника) и продолжение работы после «перезапуска» — работает. Находка: при загрузке нужно вернуть `clientConfig`, он не сериализуется.
- Ключ звонка из `mlsExporter` совпадает у всех устройств и меняется после удаления участника.
- Удалённый участник не может расшифровать следующие сообщения.
- Группа из 50 устройств создаётся одним коммитом примерно за 1 с; сообщение расшифровывается за доли миллисекунды; смена ключей участником (пустой коммит) — около 30 мс и 4,6 КБ.
- Короткое сообщение в шифрованном виде — около 320 байт.

## 5. Как это устроено

### 5.1 Устройства и ключи

- Каждое устройство (браузер, позже — Desktop и Mobile) при включении шифрования создаёт свою пару ключей подписи (Ed25519) и регистрируется: `POST /users/@me/devices` с публичным ключом и названием. Приватный ключ не покидает устройство (IndexedDB, неэкспортируемый ключ WebCrypto там, где возможно).
- Устройство выкладывает пачку одноразовых **KeyPackage** (`POST /users/@me/devices/:id/key-packages`) — по ним его добавляют в беседы. Сервер раздаёт каждую не больше одного раза и просит пополнить запас, когда он кончается; последняя хранится как «запасная».
- Участник беседы в MLS — это **устройство**, а не пользователь: у пользователя с тремя устройствами в группе три листа. Новое устройство добавляет в беседы любое другое устройство этого пользователя (или любой участник, увидев его в списке устройств).

### 5.2 Сервер как служба доставки

- Сервер хранит и раздаёт MLS-сообщения по порядку: коммиты, приглашения (Welcome) и зашифрованные сообщения. Содержимое ему недоступно.
- **Порядок коммитов** решает сервер: коммит принимается, только если он для текущей эпохи группы; из двух одновременных побеждает первый, второй клиент получает `STALE_EPOCH`, применяет чужой коммит и повторяет свой.
- Зашифрованное сообщение — это обычная строка в `messages` с пустым `content` и полем `ciphertext`; реакции, закрепления, ответы и удаление остаются серверными (реакции на первом этапе видны серверу; их шифрование — этап 2).
- Права в беседе (кто участник, кто может добавлять) проверяет сервер, как сейчас; MLS гарантирует, что читать могут только устройства, реально добавленные в группу.

### 5.3 Проверка собеседника

- **Коды безопасности:** для пары пользователей — число из отпечатков их ключей, которое можно сравнить вслух или по QR-коду.
- Чтобы новые устройства собеседника не требовали каждый раз новой проверки — **ключ пользователя** (cross-signing, как в Matrix): им подписываются его устройства; проверив пользователя один раз, доверяешь всем его подписанным устройствам.
- Новое неподписанное устройство в беседе или смена ключа — заметное предупреждение в беседе.

### 5.4 Звонки

- LiveKit E2EE (свой провайдер ключей поверх `BaseKeyProvider` + воркер `livekit-client/e2ee-worker`): медиа шифруется в браузере, LiveKit пересылает его, не расшифровывая.
- Ключ звонка = `mlsExporter(эпоха группы, "chinchi call", id группы)`; при смене эпохи (кто-то вышел или добавлен) ключ меняется у всех. Ключ эпохи кладётся в слот `эпоха mod 16`: пока остальные переходят на новый ключ, кадры со старым ещё расшифровываются, и звук не прерывается.
- Устройство, которое ещё не впустили в беседу, позвонить не может: нет ключа — нет звонка.
- Поддержка браузерами — через `RTCRtpScriptTransform` (Chrome, Firefox, Safari в актуальных версиях); если браузер не умеет, звонок в зашифрованной беседе в нём недоступен (а не идёт без шифрования).
- Ограничение: записи звонков на сервере в зашифрованной беседе быть не может (её и так нет).

### 5.5 Файлы

- Клиент шифрует файл случайным ключом AES-256-GCM (свой ключ и nonce на каждый файл) и загружает в S3 уже шифротекст под именем `encrypted` и типом `application/octet-stream`; ключ, nonce, имя, тип и размер лежат внутри зашифрованного сообщения. Сервер не знает ни содержимого, ни имени. Отдельный хэш не нужен: тег GCM не даёт подменить шифротекст.
- Получатель скачивает шифротекст и расшифровывает у себя. Картинку показывает, только если по сигнатуре это PNG, JPEG, GIF или WebP (`detectImageType` из `@chinchi/shared`, как и на сервере); остальное — скачивание под настоящим именем. Серверный воркер превью такие файлы не трогает: в шифротексте нет картинки.
- Вычистка метаданных фото (EXIF, геометка) на клиенте до шифрования — _отложено: этап 2_; пока фото уходит как есть, но видят его только участники беседы.

### 5.6 Резервная копия и история

- Без копии новое устройство не видит сообщений до своего входа в беседу — это свойство MLS.
- **Резервная копия** (второй этап): клиент хранит на сервере свою расшифрованную историю, заново зашифрованную ключом из **фразы восстановления** (12–24 слова, создаётся при включении шифрования). Новое устройство с фразой скачивает и расшифровывает историю. Сервер хранит только шифротекст.
- Потеряны все устройства и фраза — история зашифрованных бесед потеряна. Это нужно сказать пользователю прямо.

## 6. Шифрование хранения (для всего остального)

- **Файлы в S3:** SSE-S3 RustFS с локальным KMS ([документация](https://docs.rustfs.com/security-compliance/encryption/sse-s)): ключ на каждый объект, обёрнутый ключом KMS `default`, который обёрнут мастер-ключом `S3_KMS_MASTER_KEY` из `.env` (не из тома с данными). В `docker-compose.yml` включено по умолчанию (`S3_ENCRYPTION=on`). Ключ `default` RustFS сам не создаёт, поэтому сервер при старте создаёт его через admin API RustFS (`/rustfs/admin/v3/kms/key/create`, подпись SigV4 ключами хранилища; другие S3 отвечают 404 и управляют ключами сами) и ставит бакету шифрование по умолчанию. Presigned-загрузки из браузера работают как раньше: заголовки не нужны, шифрует RustFS. Интеграционный тест проверяет `ServerSideEncryption: AES256` у загруженного браузером объекта, e2e идёт с шифрованием.
- **Postgres и диск:** инструкция по шифрованию диска (LUKS / BitLocker / шифрование тома у облачного провайдера) — в [self-hosting.md](self-hosting.md#шифрование-данных). Шифрование отдельных полей в базе не делаем: ключ лежал бы рядом на том же сервере.
- **Бэкапы** (скрипты — фаза 16): архив шифруется (`age`) ключом, который хранится вне сервера.

## 7. План реализации

**Этап 1 — v0.8:**

1. `packages/e2ee`: обёртка над ts-mls (группы, устройства, сохранение состояния, вывод ключа звонка), тесты на векторах RFC.
2. Сервер: устройства и KeyPackage, служба доставки MLS (порядок коммитов, Welcome, зашифрованные сообщения), тип беседы «зашифрованная».
3. Веб: ключи устройства в IndexedDB, создание зашифрованной беседы и группы, чтение и отправка, добавление своих новых устройств, предупреждения о новых устройствах.
4. Звонки в зашифрованных беседах через LiveKit E2EE.
5. Файлы в зашифрованных беседах.
6. Шифрование хранения: SSE в RustFS, инструкция по дискам.
7. Коды безопасности.

**Этап 2 — v0.9 (решено: до v1.0, фаза 16):** фраза восстановления и резервная копия истории, ключ пользователя (cross-signing), шифрование реакций, локальный поиск по зашифрованным беседам, внешняя проверка реализации.
